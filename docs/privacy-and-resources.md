# 隐私与资源检查

## 数据位置与发布范围

- 登录 Cookie 存在 macOS 钥匙串 `io.github.kcxain.BMusic` / `bilibili-session`。网络使用临时会话，退出登录清除该项和会话 Cookie。
- 本地音乐库和播放快照在 `~/Library/Application Support/BMusic/`。搜索历史与偏好存在应用 UserDefaults。用户数据目录参与应用使用，发布脚本只打包 `dist/BMusic.app`。
- 发布检查扫描 Git 公开历史和 ZIP 文件：个人用户名、用户状态文件、凭据字面值、私钥及本机路径。GitHub 用户名和仓库地址作为公开产品标识保留。
- 0.1.0 初始提交曾使用本机 Git 邮箱；发布二进制曾包含本机路径的调试信息。此次改为 GitHub noreply 提交身份，清理公开分支和标签，发布包剥离调试信息。历史链接、第三方克隆与平台缓存仍可能保留旧元数据，清理仓库引用无法撤回外部副本。
- README 使用产品 Logo，避免展示个人头像、账号、播放历史和歌单截图。
- 更新签名私钥保存在发布机器钥匙串，应用只携带公钥。当前发布流程通过本地签名生成附件，CI 仅运行测试和构建。

## 内存与磁盘

- 图片解码缓存 8 MiB，音频段 4 MiB，文件头 512 KiB，接口响应 768 KiB；这些限额约束缓存数据。AVFoundation、可见图像、系统视图与正在下载的数据另占内存。
- 图片响应最大 8 MiB、单次音频读取最大 16 MiB。接收响应时检查状态和长度，并在每块数据到达时执行总量限制，异常响应取消下载。
- 音频服务只监听本机回环地址，使用随机路径令牌，最多 12 个连接。切歌或清空队列释放音源，停止服务并取消网络任务。
- 音频下载使用临时会话及内存缓存。播放快照仅在正常退出保存，内容相同跳过写入。收藏和歌单变更合并保存；搜索历史最多 20 条、最近播放最多 100 首。
- 图片 HTTP 磁盘缓存预算 48 MiB，首页榜单单份缓存最多 256 KiB。Sparkle 按需下载更新包，下载大小与应用包相关；自动下载默认关闭。
- 后台请求使用 ResourcePool 管理并发和最后一个消费者取消，正在退出的任务保持占用槽位直到真正结束。播放控制和主窗口各自为应用生命周期单例。

## 验证边界

44 项测试报告通过，新增分块超限、响应状态与取消测试，原有测试覆盖缓存预算、失效、任务取消、过期封面以及本机音频分段传输。短时内存采样和静态生命周期检查用于定位具体问题；长时间播放、系统缓存回收和真实 CDN 异常仍需持续观察。

### 2026-11-16 实测

- 带 Sparkle 的空闲测试构建，30 秒 RSS 采样中位数 65.83 MiB、峰值 66.52 MiB。
- 系统 `leaks` 报告 0 leaks / 0 leaked bytes；该结果限于当前进程快照，持续播放与操作仍需长期观察。
- 观察期间播放快照 mtime 保持不变。
- 本机从带更新器的 0.1.1 测试构建，通过 GitHub 发布源自动更新至正式 0.1.2 / build 36，并重启。队列条数、当前歌曲、播放进度及音乐库文件哈希与更新前一致。
- 更新后可执行文件与正式发布构建逐字节一致，应用签名校验通过。
- 应用内验证自动检测代理模式；独立使用相同代理代码验证手动 7890 请求，更新信息返回 HTTP 200。
- Git 公开分支和发布标签以及 0.1.2 安装包扫描未发现个人 B 站用户名、用户数据文件或本机目录路径。
